# Milestones

> 문서 상태: Draft 0.1  
> 최종 갱신: 2026-07-21  
> 목적: 기능 목록이 아니라 구현 순서와 각 단계의 완료 조건을 고정한다.

## 운영 규칙

- 한 마일스톤은 이전 마일스톤의 완료 조건을 깨뜨리지 않아야 한다.
- 완료는 “화면에 보임”이 아니라 자동 테스트 또는 재현 가능한 검증 절차로 판단한다.
- 판정 규칙 변경 시 `RhythmSystem.md`와 테스트를 같은 작업 범위에서 갱신한다.
- 채보 필드 변경 시 `ChartFormat.md`, 에디터, 런타임 로더의 호환성을 함께 확인한다.
- 미정 사항 때문에 전체 구현을 막지 말고 임시값을 문서에 표시한 뒤 진행한다.

## M1. DSP Clock과 오디오 예약 재생

### 목표

오디오가 예약된 DSP 시각에 시작되고, 프레임과 독립적인 곡 시간을 얻는다.

### 구현

- `RhythmClock`
- `AudioPlaybackService`
- `AudioSource.PlayScheduled`
- 시작 lead-in
- Pause/Resume 시 시작 기준 보정
- 개발자용 DSP/곡 시간 표시

### 완료 조건

- [ ] 오디오 시작 전 예약 시각을 기록한다.
- [ ] 현재 곡 시간이 `AudioSettings.dspTime` 기준으로 증가한다.
- [ ] `Time.deltaTime` 누적값을 곡 시간으로 사용하지 않는다.
- [ ] 3초 일시정지 후 재개해도 곡 시간이 일시정지 직전 위치에서 이어진다.
- [ ] 재시작할 때 새로운 DSP 시작 시각으로 다시 예약한다.
- [ ] 곡 시작과 재시작을 20회 반복해 예외나 중복 재생이 없다.

### 제외

- 실제 노트 판정
- 점수
- 완성 UI

## M2. 10레인 입력 수집

### 목표

10개 키의 Down/Up 이벤트와 이벤트 시각을 손실 없이 큐에 저장한다.

### 구현

- `InputRouter`
- 키-레인 매핑
- `RhythmInputEvent`
- `InputEventQueue`
- Input System 시간과 DSP 시간 변환
- 키 자동 반복 제거
- 전체 키 해제 대기 상태

### 완료 조건

- [ ] 10개 레인이 각각 올바른 기본 키에 대응한다.
- [ ] Down과 Up이 구분된다.
- [ ] 키를 길게 눌러도 Down 이벤트가 반복 생성되지 않는다.
- [ ] 같은 프레임의 여러 입력이 개별 이벤트로 저장된다.
- [ ] 이벤트는 시각과 sequence 순서로 결정적으로 정렬된다.
- [ ] 일시정지와 재시작 시 입력 큐가 비워진다.
- [ ] 입력 테스트 화면 또는 디버그 로그로 10키 입력을 확인할 수 있다.

### 테스트

- 단일 키 Down/Up
- 10키 동시 Down
- 키 홀드 중 자동 반복 없음
- 같은 시각 이벤트의 sequence 정렬

### 완료 조건

- [ ] 정상 샘플 채보를 RuntimeChart로 변환한다.

- [ ] `lane < 0`, `lane >= 10`을 거부한다.

## M4. Tap 판정 코어

### 목표

화면 표시 없이도 입력 이벤트와 채보만으로 Tap 판정 결과를 만든다.

### 구현

- `JudgementSettings`
- 레인별 후보 검색
- Perfect/Great/Good/Bad/Miss
- Early/Late
- 자동 Miss
- 입력 1개당 노트 1개 소비
- 판정 결과 로그

### 완료 조건

- [ ] `±25ms` 경계가 Perfect다.
- [ ] `25ms 초과~50ms`가 Great다.
- [ ] `50ms 초과~90ms`가 Good이다.
- [ ] `90ms 초과~120ms`가 Bad다.
- [ ] `+120ms` 초과 미입력 노트가 Miss다.
- [ ] `-120ms`보다 이른 입력은 노트를 소비하지 않는다.
- [ ] 가장 가까운 노트를 선택하고 동률이면 이른 노트를 선택한다.
- [ ] 한 입력이 두 노트를 판정하지 않는다.
- [ ] 서로 다른 레인의 동시 노트를 독립적으로 판정한다.
- [ ] 동일한 입력 기록을 반복 실행하면 동일한 결과가 나온다.

### 필수 자동 테스트

- 각 판정의 음수/양수 경계
- 경계 바로 안쪽과 바깥쪽
- 근접 노트 선택
- 동시 10레인
- 자동 Miss 다중 처리
- 빈 입력

## M5. 프레임 드롭 내성 검증

### 목표

판정이 입력 처리 프레임이 아니라 입력 이벤트 시각을 사용한다는 것을 검증한다.

### 구현

- 인위적 메인 스레드 정지 디버그 명령
- 입력 큐 지연 처리 테스트
- 한 프레임 다중 자동 Miss 처리
- 성능 로그

### 완료 조건

- [ ] 메인 스레드를 200ms 정지해도 저장된 이벤트가 원래 시각으로 판정된다.
- [ ] 정지 중 기한이 지난 모든 노트가 복귀 프레임에 누락 없이 처리된다.
- [ ] 화면 노트가 건너뛰어 이동해도 판정 결과에는 영향이 없다.
- [ ] 렌더링 Prefab이 없는 상태에서도 같은 판정 테스트가 통과한다.
- [ ] 프레임 드롭 전후의 deltaMs 계산이 예상값과 일치한다.

## M6. Hold 판정

### 목표

Hold 시작, 유지, 조기 해제, 정상 완료를 일관되게 처리한다.

### 구현

- Hold 시작 판정
- 레인별 pressed 상태
- Hold 진행 상태
- `HoldBreak`
- 종료 자동 완료
- 중첩 검증

### 완료 조건

- [ ] 시작 입력은 Tap과 같은 판정 구간을 사용한다.
- [ ] 시작 Miss면 Hold 전체가 실패한다.
- [ ] 키를 계속 누르면 종료 시 정상 완료된다.
- [ ] 종료 90ms보다 일찍 놓으면 HoldBreak다.
- [ ] 종료 90ms 이내에 놓으면 정상 완료다.
- [ ] 키 자동 반복이 Hold 상태에 영향을 주지 않는다.
- [ ] 재시작 뒤 이전 Hold 상태가 남지 않는다.

### 미정 확인

- Hold 종료에 별도 점수를 줄지
- Hold tick을 도입할지
- Hold 위 중첩 노트를 지원할지

## M7. 플레이 화면과 노트 표시

### 목표

판정 시스템을 변경하지 않고 플레이 가능한 시각 표현을 붙인다.

### 구현

- Gameplay Scene
- LaneField
- 10개 LaneView
- 판정선
- Tap/Hold Prefab
- Object Pool
- NoteScheduler
- NotePresenter
- 키 입력 효과
- 판정 효과

### 완료 조건

- [ ] 10개 레인이 화면 왼쪽에서 오른쪽 순서로 표시된다.
- [ ] 노트가 목표 시각에 판정선에 도달한다.
- [ ] 노트 속도 변경이 판정 시각을 바꾸지 않는다.
- [ ] Visual Offset이 판정에 영향을 주지 않는다.
- [ ] 화면 밖 노트가 불필요하게 활성화되지 않는다.
- [ ] 노트 생성과 제거에 Object Pool을 사용한다.
- [ ] 1,000개 이상의 샘플 노트에서 지속적인 GC 할당 급증이 없다.

- [ ] 결과의 판정별 합계가 전체 노트 수와 일치한다.
- [ ] 정확도 계산에 0으로 나누는 오류가 없다.
- [ ] 재시도하면 결과가 초기화된다.

## M9. 일시정지, 포커스, 재시작

### 목표

플레이 흐름을 끊는 상황에서 시간과 입력 상태가 오염되지 않는다.

### 구현

- PauseField
- 자동 포커스 감지
- 수동 재개
- 3초 재개 카운트다운
- 전체 키 해제 확인
- 세션 재시작
- 곡 선택 복귀

### 완료 조건

- [ ] 일시정지 중 곡 시간, 자동 Miss, 콤보가 진행되지 않는다.
- [ ] 포커스 이탈 시 자동 일시정지한다.
- [ ] 포커스 복귀만으로 자동 재개하지 않는다.
- [ ] 재개 전 입력 큐를 비운다.
- [ ] 눌린 채로 복귀한 키가 즉시 새 입력으로 판정되지 않는다.
- [ ] 재시작 뒤 오디오, 입력, 노트, 점수 상태가 모두 초기화된다.
- [ ] 일시정지와 재시작을 반복해도 곡 시간이 누적해서 틀어지지 않는다.

## 현재 우선순위

```text
M0 문서/기반
  -> M1 DSP Clock
  -> M2 입력 이벤트
  -> M3 채보 로드
  -> M4 Tap 판정
  -> M5 프레임 드롭 검증
  -> M6 Hold
  -> M7 화면 표시
  -> M8 점수/결과
  -> M9 흐름 제어
  -> M10 오프셋
  -> M11 데모
```

핵심 원칙은 **화면을 먼저 만드는 것이 아니라 시간과 판정의 신뢰성을 먼저 증명하는 것**이다.
